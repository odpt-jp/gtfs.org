	公式の仕様、リファレンスおよびドキュメントは英語で記述されています。異なる言語への翻訳が英語の原文と異なる場合、英語の原文が優先されます。すべてのコミュニケーションは英語で行われます。

GTFS標準は不変のものではありません。これは、GTFSを積極的に利用する交通事業者、開発者、その他の利害関係者のコミュニティによって開発および維持されるオープンな仕様です。GTFSデータの作成者および利用者からなるこのコミュニティが進化し続けるにつれて、新しい機能をサポートするために仕様を拡張する提案が期待されます。このプロセスを管理するため、GTFSガバナンスフレームワークが確立されています。

GTFSガバナンスとは、GTFSがどのように維持、更新、開発されるかを導くフレームワークを指します。これは、意思決定を導くためにコミュニティが確立したルールおよびプロセスを包含し、GTFSがオープンで協働的なデータ標準であり続けることを保証します。

GTFSのガバナンスフレームワークは、以下の要素で構成されます。

* [指導原則](guiding-principles.md)  
* [役割と責任](roles.md)  
* [変更の種類](change-types.md)
* [変更プロセス](change-process.md)

<img class="center" width="1000" height="100%" src="../../../../../assets/governance-intro.svg">

特に、GTFS変更プロセスは、GTFSへの修正または追加がコミュニティによって提案、議論、承認される手順です。このプロセスにより、仕様が安定的、予測可能かつ協働的な方法で進化することが保証されます。

## 仕様変更とは何ですか？ {: #what-is-a-specification-change}


変更とは、[Google/transit repository](https://github.com/google/transit) でホストされている GTFS ドキュメントに対して提案されるあらゆる修正を指します。このような変更には、新しい機能の追加、既存のファイルまたはフィールドの更新、ガイドラインの明確化、または例の改善が含まれることがあります。**本質的には、変更を提案することは、仕様を改善または拡張するために、ドキュメントに関連するあらゆるファイル、特に Reference.md ファイルの内容を変更することを提案することを意味します。**

## どのように参加を始められますか？ {: #how-can-i-start-participating}


誰でもGTFSの開発に貢献できます。通常、仕様を改善するための提案やアイデアを持つ人は、[変更プロセス](change-process.md)で概説されている手順に従い、提案を洗練し、前進させます。

プロセスを効果的に進めるには、実施すべき具体的な手順を決定するさまざまな[変更の種類](change-types.md)を理解することが重要です。そのため、貢献者は、自身の参加および関与をよりよく理解するために、これらの変更カテゴリと[役割と責任](roles.md)をよく理解することが推奨されます。

### 変更プロセスは通常どのようなものですか？ {: #what-does-the-change-process-typically-look-like}


前述のとおり、異なる[変更の種類](change-types.md)には異なるプロセスが適用されます。以下は、コミュニティが GTFS 仕様に対する機能的変更を提案、レビュー、テスト、および採用する方法を示す、[機能的変更](change-types.md/#functional-changes)のプロセスの概要です。

| アクション                      | 説明                                                                                                  | 期間            | 条件                                                                                         |
| --------------------------- | ------------------------------------------------------------------------------------------------------------ | --------------- | -------------------------------------------------------------------------------------------------- |
| 提案の提出             | 変更を提案するために、GTFS リポジトリで Pull Request (PR) が作成されます。                                  | —               | 誰でも提案を提出することができます。                                                                      |
| コミュニティでの議論        | コミュニティが提案について議論し、改善します。                                                                | 最低 7 日間  | オープンな参加。                                                                                |
| レビュー期間               | 貢献者および Maintainer が、明確性、実現可能性、および GTFS の目標との整合性について提案をレビューします。 | 最低 7 日間  | Maintainer および貢献者がレビューしなければなりません。                                                           |
| テスト承認のための投票 | コミュニティが、提案がテストの準備ができているかどうかを判断するために投票します。                                      | 最低 14 日間 | 少なくとも 5 人の貢献者（うち 2 人以上の Producers および 2 人以上の Consumers を含む）が必要であり、全員が賛成票を投じなければなりません。          |
| First Adopters によるテスト      | 選定された First Adopters が、実環境またはシミュレーション環境で提案された変更をテストします。                   | 最低 7 日間  | 少なくとも 1 つの Producer および少なくとも 1 つの Consumer が変更をテストしなければなりません。                                 |
| 採用のための最終投票     | コミュニティが変更を正式に採用するために投票します。可決には 80% 以上の承認が必要です。                              | 最低 14 日間 | 少なくとも 5 人の貢献者（うち 2 人以上の Producers および 2 人以上の Consumers を含む）が必要であり、少なくとも 80% が賛成票を投じなければなりません。 |
| 採用                    | 承認された変更が、Maintainer により GTFS 仕様に正式に追加されます。                         | —               | Maintainer が公式ドキュメントを更新します                                                  |


[非機能的変更](change-types.md/#non-functional-changes)および[ドキュメント保守](change-types.md/#documentation-maintenance)には、短縮されたプロセスがあります。詳細については、完全な[変更プロセス](change-process.md)を参照してください。
