	公式の仕様書、リファレンスおよびドキュメントは英語で作成されています。翻訳版と英語版の内容に相違がある場合は、英語版が優先されます。すべてのコミュニケーションは英語で行われます。

GTFS 標準は固定されたものではなく、交通事業者、開発者、その他の関係者によって構成されるコミュニティによって開発・維持されているオープンな仕様です。この GTFS データの提供者および利用者のコミュニティが進化を続ける中で、新しい機能をサポートするための仕様拡張提案が行われることが想定されています。このプロセスを管理するために、GTFS のガバナンスフレームワークが確立されています。

GTFS ガバナンスとは、GTFS がどのように維持・更新・開発されるかを導くための枠組みを指します。これは、GTFS がオープンで協調的なデータ標準であり続けることを保証するために、コミュニティによって定められた意思決定のためのルールとプロセスを包含しています。

GTFS のガバナンスフレームワークは、以下の要素で構成されています。

* [基本原則](guiding-principles.md)  
* [役割と責任](roles.md)  
* [変更の種類](change-types.md)
* [変更プロセス](change-process.md)

特に、GTFS 変更プロセスは、GTFS に対する修正や追加をコミュニティが提案・議論・承認するための手続きです。このプロセスにより、仕様が安定的かつ予測可能で、協調的な方法で進化していくことが保証されます。

## 仕様変更とは何ですか？ {: #what-is-a-specification-change}

変更とは、[Google/transit リポジトリ](https://github.com/google/transit)でホストされている GTFS ドキュメントに対して提案されるあらゆる修正を指します。これには、新しい機能の追加、既存のファイルやフィールドの更新、ガイドラインの明確化、または例の改善などが含まれる場合があります。**本質的には、変更を提案するということは、仕様を強化または拡張するために、特に Reference.md ファイルをはじめとするドキュメント関連ファイルの内容を変更することを提案することを意味します。**

## どのように参加を始めることができますか？ {: #how-can-i-start-participating}

誰でも GTFS の開発に貢献することができます。通常、仕様の改善に関する提案やアイデアを持つ人は、[変更プロセス](change-process.md) に記載された手順に従って、自身の提案を洗練させ、進めていきます。

このプロセスを効果的に進めるためには、取るべき具体的な手順を決定する [変更の種類](change-types.md) を理解することが重要です。そのため、貢献者はこれらの変更カテゴリや [役割と責任](roles.md) に精通し、自身の参加方法や関与の仕方をよりよく理解することが推奨されます。

### 変更プロセスは通常どのような流れですか？ {: #what-does-the-change-process-typically-look-like}

前述の通り、異なる[変更の種類](change-types.md)によって異なるプロセスが適用されます。以下は、GTFS 仕様に対する[機能的変更](change-types.md/#functional-changes)の提案、レビュー、テスト、採用の流れを示した概要です。

| アクション                  | 説明                                                                                                      | 期間            | 条件                                                                                              |
| --------------------------- | --------------------------------------------------------------------------------------------------------- | --------------- | ------------------------------------------------------------------------------------------------- |
| 提案の提出                 | 変更を提案するために、GTFS リポジトリに Pull Request (PR) を作成します。                                 | —               | 誰でも提案を提出することができます。                                                              |
| コミュニティでの議論       | コミュニティが提案について議論し、内容を洗練します。                                                     | 最低 7 日間     | 誰でも参加可能です。                                                                              |
| レビュープロセス           | コントリビューターおよびメンテナーが、提案の明確さ、実現可能性、GTFS の目的との整合性を確認します。     | 最低 7 日間     | メンテナーおよびコントリビューターがレビューしなければなりません。                               |
| テスト承認のための投票     | コミュニティが提案がテストに進む準備ができているかどうかを投票で決定します。                           | 最低 14 日間    | 少なくとも 5 名のコントリビューター（うち 2 名以上の Producer と 2 名以上の Consumer を含む）が全員賛成する必要があります。 |
| ファーストアダプターによるテスト | 選定されたファーストアダプターが、実環境またはシミュレーション環境で提案された変更をテストします。     | 最低 7 日間     | 少なくとも 1 名の Producer と 1 名の Consumer が変更をテストしなければなりません。               |
| 採用のための最終投票       | コミュニティが正式に変更を採用するかどうかを投票で決定します。可決には 80%以上の賛成が必要です。       | 最低 14 日間    | 少なくとも 5 名のコントリビューター（うち 2 名以上の Producer と 2 名以上の Consumer を含む）のうち、少なくとも 80% が賛成しなければなりません。 |
| 採用                       | 承認された変更がメンテナーによって正式に GTFS 仕様に追加されます。                                       | —               | メンテナーが公式ドキュメントを更新します。                                                        |

[非機能的変更](change-types.md/#non-functional-changes)および[ドキュメント保守](change-types.md/#documentation-maintenance)には、短縮されたプロセスが存在します。詳細については、完全な[変更プロセス](change-process.md)をご参照ください。
