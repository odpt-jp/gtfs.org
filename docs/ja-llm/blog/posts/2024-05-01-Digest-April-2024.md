## 🗳️ 現在投票中 {: #currently-voting}


**[ルートベースの fare_rules における stops.zone_id の条件付き要件を明確化 #432](https://github.com/google/transit/pull/432)** \
この提案は、stops.zone_id の条件付き要件を変更し、停留所等(stop)が、fare_id と route_id のみが定義された fare_rules.txt レコード（ルートベースの運賃）に route_id が存在する trip_ids にのみ割り当てられているシナリオを許容します。



* 投票は 2024-04-30 23:59:59 UTC に終了します。

## 📂 アクティブな提案 {: #active-proposals}


**[google/transit リポジトリに Best Practices のソースドキュメントを追加 #447](https://github.com/google/transit/pull/447)**

この PR は、参照ドキュメントをこのリポジトリに集約し、Best Practices の可視性を高めるために、Best Practice ドキュメントをこのリポジトリに追加します。GTFS Realtime Best Practices も、読みやすくするために1つの単一ドキュメントに集約されました。 

**[[GTFS-Fares v2] fare_leg_join_rules.txt を追加（第1版） #439](https://github.com/google/transit/pull/439)**

実際の運賃体系では、運賃が出発地点と終着地点（または通過するゾーン）のみに依存し、その間にどのような一連の乗車区間(leg)や乗換を行うかを考慮しないことが一般的なシナリオです。複数の乗車区間(leg)を「有効運賃区間(effective fare leg)」に結合するためのルールは、fare_leg_join_rules.txt で定義できます。

この PR は現在、同じネットワーク内の乗車区間(leg)の結合のみを許可しています。ワーキンググループは将来、追加の機能（異なるネットワークの乗車区間(leg)、停留所等(stop)の組み合わせなどの結合など）によって、このファイルを拡張することができます。

**[GTFS real time FeedHeader に Feed Version と GTFS url を追加 #434](https://github.com/google/transit/pull/434)**

この Realtime 提案では、GTFS real time データとともに使用する GTFS schedule ファイルに関する情報を提供するため、feed header に2つの新しいフィールドを追加します。feed_version は GTFS の feed_info.txt ファイル内の feed_version と一致し、GTFS_url は GTFS ファイルの url を指します。この変更を実装する意思のある producer が、進めるために必須です。

## 🔥 最も活発な議論 {: #most-active-conversations}


**[UTF-8 を必須の GTFS エンコーディングにする #444](https://github.com/google/transit/issues/444)**

Stefan は、プロデューサーがさまざまなエンコーディングを使用し、さらにはそれらを混在させていることについて懸念を示しました。これはコンシューマーにとってデータ処理上の問題につながります。この問題に対処するため、UTF-8 の使用を明確に必須とすることを提案しました。

**[GTFS 用語の改善：「Schedule」から「Static」への移行 #442](https://github.com/google/transit/issues/442) **

MobilityData は、多くの人が「Schedule」と「Static」という用語を同じ意味で使用しているため、GTFS Schedule に関する用語を統一することを提案しています。



* 公式用語として「Static」を使用することについて、ある程度の合意があります。
* 「Static」と「Schedule」の両方を廃止することを検討する人もいます。

議論に参加し、皆様のご意見をお聞かせください。

**[GTFS における駅モデリングの改善 #438](https://github.com/google/transit/issues/438)**

最近、MobilityData は駅モデリングに関する制約や困難を指摘するフィードバックを受けています。例として、停留所等(stop)が入口を通過する必要があるかどうかを示す明確な仕組みがないこと、検索および可視化における混乱が挙げられます。議論の中で、コミュニティはより上位の階層を追加する可能性についても言及しています。しかし、コミュニティメンバーによって現在の location_type=1(station) の解釈が異なることも判明しています。この Issue で駅モデリングについて皆様のご意見をお聞かせください！

**[[Governance] フェーズ 2：投票とレビューの強化 #436](https://github.com/google/transit/issues/436)**

この GitHub Issue は、GTFS Governance を強化する継続的な取り組みの一部であり、特に 2023 年 12 月に公開された[段階的計画](https://github.com/google/transit/issues/413)のフェーズ 2 で概説された仕様改定プロセスに焦点を当てています。



* 2024 年 3 月 13 日にインタラクティブな議論が開催されました。参加者はフィードバックを共有し、いくつかの大まかな合意に達しました。
* ワーキンググループが結成され、[2024 年 5 月 2 日木曜日 午前 11 時 EDT](https://www.eventbrite.ca/e/gtfs-governance-working-group-meeting-may-2nd-11-am-edt-tickets-890410801677?aff=oddtdtcreator)に会議が開催されます。

**[pathways.stair_count の制約の明確化 #437](https://github.com/google/transit/issues/437)**

Michael Kearney は pathways.stair_count の定義に関する潜在的な問題を指摘し、空の値および 0 の値の意味についていくつかの疑問を提起しています。その後、議論のために 4 つの可能な解決策を提案していますが、後方互換性に関する潜在的な問題も指摘しています。この Issue には、コミュニティによるさらなる議論が必要です。
