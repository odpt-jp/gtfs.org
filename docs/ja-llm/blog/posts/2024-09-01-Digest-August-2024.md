# [GTFS Digest] 2024年8月 - GTFS.orgの新デザインと2件の投票 {: #gtfs-digest-august-2024-a-new-design-for-gtfsorg-and-2-votes-on-the-block}


今月のGTFS Digestでは、ナビゲーションの改善とコミュニティセクションを備えたGTFS.orgの新デザインを取り上げます。conditional stops.txtや推奨される行先表示(headsign)などの最近の更新、ポリゴンの有効性および乗換に関する明確化について進行中の投票、ならびに便(trip)のスケジューリングに関する主要な議論を扱います。GTFS Flex WebinarとGTFS-Fares v2 Meetingをお見逃しなく。最新情報を確認し、議論に参加してください！

## 📢 お知らせ {: #announcements}


[**GTFS.org がリニューアルされました**](http://GTFS.org)  
GTFS.org を、GTFS に関するあらゆる情報を得るために訪れる唯一の場所にするべく、フィードバックの収集と改善に精力的に取り組んできました。

交通機関の仕様を初めて利用する方でも、経験豊富な GTFS ユーザーでも、GTFS.org には必要なものがすべて揃っています。

初回訪問時には、以下の変更をご確認いただけます。

* 訪問者をより適切に案内するための新しいデザインとナビゲーション。   
* GTFS とその Features の基本を紹介する Getting Started セクション。   
* GTFS の開発に参加するための Community Section。   
* [**Blog Section における GTFS Digest の新しいホーム**](https://gtfs.org/blog/)。

## 🚀 最近採用された変更 {: #recently-adopted}


[**デマンド型サービスに伴う stops.txt の存在要件の変更 #472**](https://github.com/google/transit/pull/472)  
この PR は、flex の採用後に stops.txt の存在要件を更新し、必須から条件付き必須（locations.geojson が存在しない場合は必須、それ以外の場合は任意）へ変更することを提案しています。

[**行先表示(headsign)が推奨であることの追加 #485**](https://github.com/google/transit/pull/485)  
この PR は、ルート・路線系統(route)内の便(trip)を区別するために使用される可能性がある、車両に行先表示(headsign)テキストが表示されるすべてのサービスについて、行先表示(headsign)を推奨する旨の記述を追加することを提案しています。

## 🗳️ 現在投票中 {: #currently-voting}


[**locations.geojson のポリゴンに有効性ルールを追加 #476**](https://github.com/google/transit/pull/476)  
この PR は、GTFS においてポリゴンが無効となり得るすべての方法を記述する代わりに、flex ポリゴンの有効性ルールを改善するため、OpenGIS Simple Features Specification のセクション 6.1.11 を参照することを提案しています。

* *投票期間は 2024年9月11日（水）23:59:59 UTC に終了します*。

[**[明確化] transfers.txt における from/to_stop_id および from/to_trip_id の説明**](https://github.com/google/transit/pull/455)  
この PR は、元の意味論を変更することなく、transfers.txt における from/to_stop_id および from/to_trip_id の説明を明確化します。

* *投票期間は 2024年9月17日（火）23:59:59 UTC に終了します。*

## 📂 アクティブな提案 {: #active-proposals}


[**[GTFS Fares v2] Area Set のマッチング述語 #483**](https://github.com/google/transit/pull/483)  
現在の fare_leg_rules.txt では、出発地および目的地のエリアのみを述語として使用できますが、これではより複雑なゾーン運賃体系を効果的に記述できません。この PR では、停留所等(stop)エリアのコレクション、すなわち「area sets」を述語として追加することを提案しています。

[**CANCELED/SKIPPED TripUpdates と NO_SERVICE Alerts の明確化 #482**](https://github.com/google/transit/pull/482)  
これは活発に議論されている提案です。現在、コントリビューターは以下について議論しています。

* NO_SERVICE 運行情報(alert)を経路探索に使用できるのか、それともメッセージの提供のみを目的とするのか。  
* 仕様がコンシューマー間で異なる解釈を許容しているのか。

## 🔥 最も活発な議論 {: #most-active-conversations}


[**追加および複製された便について、StopTimeEvent で予定時刻と遅延の両方を指定できるようにする。#490**](https://github.com/google/transit/issues/490)  
miklcct は、ADDED および DUPLICATED の便について、StopTimeEvent で予定時刻と遅延の両方を指定できるよう、GTFS-RT 仕様を更新することを提案しました。この変更により、特に臨時サービスまたは複製サービスにおいて、これらの種類の便の予定時刻を示せないという現在の制限に関する問題に対処できます。この提案は、既存システムとの互換性を維持しつつ、柔軟性を向上させることを目的としています。

[**便に行先表示(headsign)がないことを明示的に伝達する方法を設ける。#488**](https://github.com/google/transit/issues/488)  
evansiroky は、行先表示(headsign)が提供されていない場合、車両には行先表示(headsign)がないものとみなすべきであることを明示する記述を含めるよう、仕様の文言を調整することを提案しました。

[**GTFS-RT の便の変更(trip modification)オブジェクトで、異なる arrival_time と departure_time を指定することは不可能です。#487**](https://github.com/google/transit/issues/487)  
Miklcct は、迂回旅程にある車両について、駅での延長停車時間を指定するため、ReplacementStop オブジェクトに layover フィールドを追加することを提案しています。

[**予定された増発便 #481**](https://github.com/google/transit/issues/481)  
Stefan は、事業者による確認後にのみ旅行情報サービスで利用可能となる、予定された増発便を GTFS でサポートする必要性について取り上げ、これらの便を示すために `trips.txt` へ追加の列を設けることを提案しています。また、既存の GTFS および GTFS-RT の枠組みにおける制限と、考えられる解決策についても議論しています。
