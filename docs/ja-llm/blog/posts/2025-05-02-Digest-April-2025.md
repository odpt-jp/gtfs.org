# [GTFS Digest] 2025年4月 - Trip Modificationsの明確化に投票し、無料運賃ウェビナーに参加しましょう {: #gtfs-digest-april-2025-vote-on-trip-modifications-clarifications-join-the-free-fares-webinar}


2025年4月のGTFS Digestをお届けします！今月、コミュニティはGTFS Realtimeにおける便の変更(trip modification)に関する明確化について投票しています。主な提案には、距離ベース運賃のサポート、cEMV支払いフィールド、および新しいガバナンスプロセスの更新が含まれます。複雑な運賃体系、便(trip)のモデリング、座席内乗り換えについての議論に参加してください。さらに、5月28日に開催される無料のGTFS Faresウェビナーに登録してください！

<!-- more -->

GTFS Digestは、GTFSに関する進展の概要を提供するために[MobilityData](https://mobilitydata.org/)が毎月作成しているリソースです。 

皆様からのフィードバックを大切にしており、私たちの取り組みについてご意見を伺いたいと考えています。[このフォーム](https://forms.gle/GGefktvemnJD5Q9g8)にご記入いただき、このツールの可能性を最大限に引き出すためにご協力ください。

## 🗳️ 現在投票中 {: #currently-voting}


[**便の変更に関するさらなる明確化 #542**](https://github.com/google/transit/pull/542)  
この PR は、以下を含む便の変更に関する誤解を明確にします。

* 提供される shape は完全な shape であるべきことを明記します  
* GTFS-rt 内の id の使用方法を明確化します   
* リンクされたエンティティは同じ feed 内で行うべきことを明確化します  
* TripProperties 内の shape_id の定義が、reference と proto の間で同期していませんでした

## 🚀 最近採用されたもの {: #recently-adopted}


[**booking_rules.txt における continuous pickup/dropoff の値およびフィールド Type に関する明確化 #528**](https://github.com/google/transit/pull/528)  
この PR は、デマンド型サービスに特化した明確化を導入し、start_pickup_drop_off_window/end_pickup_drop_off_window が指定されている場合に continuous_pickup/continuous_drop_off の値として 1 を使用できるようにします。

[**TripUpdate.schedule_relationship = ADDED を非推奨とし、GTFS static のスケジュールに基づいて運行されない新規／置換便を指定するために TripUpdate.schedule_relationship = NEW / REPLACEMENT を追加します。#504**](https://github.com/google/transit/pull/504)  
更新された提案は、GTFS Realtime における TripUpdate.schedule_relationship = ADDED の非推奨化と、GTFS Schedule に存在しない便を示すための TripUpdate.schedule_relationship = NEW および TripUpdate.schedule_relationship = REPLACEMENT の使用に焦点を当てており、新しい値は experimental としてフラグ付けされています。

## 📂 活動中の提案 {: #active-proposals}


[**[Governance] 新しい GTFS Schedule ガバナンス提案 #544**](https://github.com/google/transit/pull/544)  
MobilityData は、2年間にわたるコミュニティからのフィードバックに基づき、現在の GTFS ガバナンスプロセスの更新を提案しています。主な改善点には、より明確な文書化、構造化された提案フェーズ、改訂された投票要件が含まれます。 

* 投票に進む前のレビュー時間をより多く確保するため、議論期間は**さらに1か月延長**されました。


[**[GTFS-Fares v2] 距離ベース運賃の追加 #556**](https://github.com/google/transit/pull/556)  
この PR は、fare_leg_rules.txt および stop_times.txt に複数の新しいフィールドを導入し、新しい fare_leg_distance_rules.txt ファイルを追加することで、距離ベース運賃システムのモデリングを可能にする新機能を追加します。

[**trips.txt への cars_allowed フィールドの追加 #547**](https://github.com/google/transit/pull/547)  
この PR は、trips.txt に cars_allowed フィールドを追加することを提案しています。フェリーの自動車情報を GTFS に追加する方法については、[issue #466](https://github.com/google/transit/issues/466) で多くの議論がありました。議論は、stop_times.txt を用いるアプローチと trips.txt を用いるアプローチのどちらを使用するかを中心に行われました。 

[**communication_period および impact_period の追加 #546**](https://github.com/google/transit/pull/546)  
この提案では、2つの新しいフィールドを導入します。communication_period は運行情報(alert)を表示するべき時間を指定し、impact_period はサービスが障害の影響を受ける時間を指定します。さらに、一貫性を保つため、これらの新しいフィールドが active_period と相互排他的であることを保証するルールを定めます。

[**agency.txt および routes.txt への cemv_support フィールドの追加 #545**](https://github.com/google/transit/pull/545)  
この提案では、特定の事業者またはルート・路線系統(route)における交通サービスへのアクセスに、乗客が cEMV（非接触型 Europay、Mastercard、および Visa）を使用できるかどうかを示すため、agency.txt および routes.txt に新しい cemv_support フィールドを導入します。 

[**便の変更に関するさらなる明確化 #542**](https://github.com/google/transit/pull/542)  
この提案は、GTFS Realtime における便の変更(trip modification)について、ルート形状(shape)、ID の使用、およびエンティティのリンクに関するさらなる明確化を追加します。また、一貫性を保つため、TripProperties 内の shape_id の定義をリファレンスと proto の間で整合させます。

[**original_trip_id による GTFS Schedule および Realtime の強化 #534**](https://github.com/google/transit/pull/534)  
Davidr1234 は、Google Transit 拡張の `original_trip_id` を GTFS Schedule と GTFS Realtime の両方で採用することを提案しています。これにより、GTFS と、同様の概念を持つ SIRI や NeTEx などの他の標準との間で、便(trip)をシームレスに参照できるようになります。

## 🔥 最も活発な議論 {: #most-active-conversations}


[**旅行の途中で車両を連結／切り離しできるよう、着席したままの乗換に関する要件を緩和する #548**](https://github.com/google/transit/issues/548)  
Michael は、National Rail network で一般的な、旅行の途中で車両を連結／切り離す場合における、着席したままの乗換に関する現在の要件に疑問を呈しています。彼は、transfer_type = 4 の要件を緩和することを提案しています。 

[**運賃は複数のネットワークに属する #551**](https://github.com/google/transit/issues/551)  
Michael は、route_networks.txt における要件を緩和し、ルート・路線系統(route)を複数のネットワークに割り当てられるようにすることを提案しています。

[**一般的な乗換ネットワーク内で特定の駅での乗換を必要とする運賃の定義 #555**](https://github.com/google/transit/issues/555)  
Michael は、London の PAYG rail network 向けに GTFS Fares v2 で複雑な運賃ルールをモデル化するためのガイダンスを求めています。

[**Frequencies.txt の主キー: end_time、headway_secs、exact_times を追加するか？ #514**](https://github.com/google/transit/issues/514)  
この issue は、時間帯が重複し headway_secs が異なる便(trip)（ラッシュアワー中の追加バスサービスなど）、または exact_times が異なる便を対象とするため、frequencies.txt の主キーを拡張することを提案しています。

[**route_type に関する定義の拡張／追加 #310**](https://github.com/google/transit/issues/310)  
Elizabeth は、routes.txt の route_type を拡張し、bus を更新するとともに van および BRT を追加することを提案しています。

[**trips.txt に cars_allowed フィールドを追加する #466**](https://github.com/google/transit/issues/466)  
Ville Pihlava は、フェリーおよび auto train のユースケースを対象とするため、trips.txt に car_allowed フィールドを追加することを提案しています。 

[**複数形のフィールド名？ #536**](https://github.com/google/transit/issues/536)  
Nina は、GTFS において「複数」の多重度(cardinality)を持つフィールドに、複数形ではなく単数形の名前が付けられている理由を問いかけています。回答では、CSV の各行には単一の外部キー参照しか含まれないため、列名はコレクションを表すのではなく個々の行に適用されると説明されています。

[**既存の GTFS において「停留所等(stop)／駅の概念的なグループ化」を定義する機能の欠如 #438**](https://github.com/google/transit/issues/438)  
MobilityData は、駅のモデリングを改善するための[3段階の計画](https://github.com/google/transit/issues/438#issuecomment-2289511429)を提案しており、この計画に対するフィードバックを歓迎しています。大きな異論がなければ、まもなく第1段階を進めます。
