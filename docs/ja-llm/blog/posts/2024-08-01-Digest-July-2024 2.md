# [GTFS Digest] 2024年7月 - 最新情報: 3件の新規採択と注目すべき投票 {: #gtfs-digest-july-2024-stay-informed-3-new-adoptions-and-a-vote-to-watch}


主な更新には、すべてのルート・路線系統(route)ベースのサービスに対するshapes.txtの追加（#470）、stop_times.timepointについて、空の場合はtimepoint値が提供されないことを意味するという明確化（#474）、およびfeed_info.txtが条件付き必須に更新されたこと（#460）が含まれます。コミュニティでは、デマンド型サービスに関するstops.txt要件の更新について投票が行われています（#472）。

## 🚀 最近採用された変更 {: #recently-adopted}


**[shapes を含めるべきであることを追加 #470](https://github.com/google/transit/pull/470)**

この変更では、ゾーンベースのデマンド型サービスを GTFS でモデル化できるようになったため、すべての場合で推奨とする代わりに、すべてのルートベースのサービスについて shapes.txt を含めるべきであることを指定する「should」文を shapes.txt に追加します。

**[stop_times.txt の timepoint の意図された使用方法を明確化 #474](https://github.com/google/transit/pull/474)**

この変更では、stop_times.timepoint の空のセマンティクスを明確化し、空の値は stop_times.txt 内のいずれのレコードにも timepoint 値が提供されていないことを意味し、提供される場合は、時刻が関連付けられているすべてのレコードに 0 または 1 の timepoint 値が必要であることを指定します。

**[feed_info.txt の要件を更新 #460](https://github.com/google/transit/pull/460)**

この PR は、仕様の書式との整合性を高め、ファイルの要件について追加の明確化を提供するために、feed_info.txt の存在に関する説明を更新し、条件付き必須とします。

## 🗳️ 現在投票中 {: #currently-voting}


**[デマンド型サービスに伴う stops.txt の存在要件の変更 #472](https://github.com/google/transit/pull/472)**

この PR は、flex の採用後に stops.txt の存在要件を更新し、必須から条件付き必須（locations.geojson が存在しない場合は必須、それ以外の場合は任意）へ変更することを提案しています。

## 📂 アクティブな提案 {: #active-proposals}


**[headsigns が推奨であることを追加 #485](https://github.com/google/transit/pull/485)**

この PR は、ルート・路線系統(route)内の便(trip)を区別するために使用される可能性がある、車両に行先表示(headsign)テキストが表示されるすべてのサービスについて、headsigns が推奨であるという記述を追加することを提案しています。

**[[GTFS Fares v2] Area Set のマッチング述語 #483](https://github.com/google/transit/pull/483)**

現在の fare_leg_rules.txt では、出発地および目的地のエリアのみを述語として使用できますが、これではより複雑なゾーン運賃体系を効果的に記述できません。この PR は、停留所等(stop)エリアの集合、すなわち「area sets」を述語として追加することを提案しています。 \
 \
**[CANCELED/SKIPPED TripUpdates と NO_SERVICE Alerts の明確化 #482](https://github.com/google/transit/pull/482)**

この PR は、Effect.NO_SERVICE を持つ Alert が存在し、TripUpdates 内の値と競合する場合、Alerts を信頼できる情報源と見なすべきであることを明確化することを提案しています。

**[locations.geojson 内のポリゴンに対する有効性ルールの追加 #476](https://github.com/google/transit/pull/476)**

この PR は、GTFS においてポリゴンが無効となり得るすべての方法を記述する代わりに、flex ポリゴンの有効性ルールを改善するため、OpenGIS Simple Features Specification のセクション 6.1.11 を参照することを提案しています。

## 🔥 最も活発な議論 {: #most-active-conversations}


**[Scheduled reinforcement trips #481](https://github.com/google/transit/issues/481)**

Stefanは、事業者による確認後にのみ旅行情報サービスで利用可能となる、予定された増発便をGTFSでサポートする必要性について取り上げています。これらの便を示すために`trips.txt`へ追加の列を提案し、既存のGTFSおよびGTFS-RTフレームワークにおける制約と可能な解決策について議論しています。

**[Make headsigns a recommended GTFS field #480](https://github.com/google/transit/issues/480)**

このissueは、任意のGTFSフィールドに関する#461からの議論を継続するものです。本番データにおける広範な利用と有用性を理由に、`trip_headsign`フィールドを推奨とすることを提案しています。また、行先表示(headsign)がないルート・路線系統(route)における潜在的な課題を考慮し、行先表示(headsign)の有無を示す新しい`has_headsign`フィールドなどの解決策を検討しています。

**[Center coordinate or Bounding box definition in feed_info.txt #471](https://github.com/google/transit/issues/471)**

MathematicianのMustafaは、地図上でそのデータセットが表すエリアに焦点を合わせるための中心点を示すフィールドをfeed_info.txtに追加することを提案しました。
