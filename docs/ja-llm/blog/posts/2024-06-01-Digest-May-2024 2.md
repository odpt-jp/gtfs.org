## 🚀 最近採択された項目 {: #recently-adopted}


**[fare_leg_rules.txt に rule_priority を追加 #418](https://github.com/google/transit/pull/418)**

rule_priority フィールドは、一部の運賃区間照合ルールが他の照合ルールより優先される必要があるケースを表すために使用されます。さらに、rule_priority フィールドの存在は、fare_leg_rules.txt 内の他のフィールドにおける空値の意味を変更するトリガーとして機能します。

**[ルートベースの fare_rules における stops.zone_id の条件付き要件を明確化 #432](https://github.com/google/transit/pull/432)** \
この提案は、停留所等(stop)が、fare_id と route_id のみが定義された fare_rules.txt レコード（ルートベースの運賃）に route_id が存在する trip_ids にのみ割り当てられているシナリオを許容するため、stops.zone_id の条件付き要件を変更します。

## 📂 アクティブな提案 {: #active-proposals}


**[feed_info.txt の要件を更新 #460](https://github.com/google/transit/pull/460)**

この PR は、仕様の書式との整合性を高め、ファイルの要件について追加の明確化を提供するために、feed_info.txt の存在に関する説明を更新し、条件付き必須とします。

**[transfers.txt における from/to_stop_id の存在と説明を明確化 #455](https://github.com/google/transit/pull/455)**

この PR は、潜在的な混乱を避けるために、transfers.from/to_stop_id の存在を条件付き必須から必須に変更し、その説明から「forbidden」という語を削除します。

## 🔥 最も活発な議論 {: #most-active-conversations}


**[便の更新の例と参照ドキュメントの不整合？ #468](https://github.com/google/transit/issues/468)**

Niels Penneman は、便の更新の例と参照ドキュメントの間にある不整合を解明するため、皆様の協力を必要としています。 

**[trips.txt に cars_allowed フィールドを追加 #466](https://github.com/google/transit/issues/466)**

Ville Pihlava は、フェリーおよび自動車輸送列車のユースケースを対象とするため、trips.txt に car_allowed フィールドを追加することを提案しています。 

**[提案されたベストプラクティス: SCHEDULED の便では常に TripDescriptor に trip_id を含める #465](https://github.com/google/transit/issues/465)**

この提案では、データ統合を簡素化するため、GTFS Realtime の SCHEDULED の便において TripDescriptor で `trip_id` を使用することを必須とすることを提案しています。複数の識別子を使用する代替手法では、しばしば問題が発生するためです。 

**[グローバル便 ID #462](https://github.com/google/transit/issues/462)**

SKI+ の David は、NeTEx や HRDF などの他の標準との統合を改善するため、GTFS Schedule および Realtime に新しいフィールド「trip_global_id」を提案しています。これは、1日を通して有効な便識別子の必要性に対応するものです。このグローバル ID により、異なるデータ形式間での旅行情報のマッピングが容易になります。 

**[bikes_allowed を GTFS の推奨フィールドにする #461](https://github.com/google/transit/issues/461)**

GTFS Schedule において `bikes_allowed` フィールドを推奨にすることは、自転車の持ち込み対応に関するデータ精度の向上を目的としています。この変更により、このフィールドが欠落しているデータセットに対して検証通知が促され、より広範な採用が奨励されます。

**[Shapes を GTFS の推奨ファイルにする #459](https://github.com/google/transit/issues/459)**

GTFS Schedule において `shapes.txt` ファイルを推奨することで、地図ベースの表示およびデータ品質検証を改善し、その採用率が 85% であることを反映します。この変更により、ユーザー体験が向上し、リアルタイム車両追跡が支援されます。

**[GTFS static への vehicles.txt の追加 #458](https://github.com/google/transit/issues/458)**

TransSee の Darwin は、GTFS に `vehicles.txt` ファイルを追加することを提案しています。これにより、車両容量、アクセシビリティ、および機能に関する詳細情報を提供でき、リアルタイム予測ツールを強化し、車両群データ報告を標準化できる可能性があります。このファイルには、車両タイプ、容量、製造者、アクセシビリティ機能などの詳細を含めることができます。

**[非タイムポイントにおける StopTimeEvent.uncertainty の使用 #454](https://github.com/google/transit/issues/454)**

AC Transit の Michael Paine は、非タイムポイントの停留所等(stop)において `StopTimeEvent.uncertainty` フィールドを使用し、時刻表の近似を示すことを求めています。これにより、バスが早着または遅着しているように見えることによる乗客の混乱を防ぎます。この実践により、遅延値を変更せずに時刻の変動を伝達でき、乗客がバスの時刻表についてより適切に把握できるようになる可能性があります。

**[[DRT] GTFS-Flex の採用後、stops.txt は必須ファイルではなくなるべきです。 #452](https://github.com/google/transit/issues/452)**

GTFS-Flex の導入により、GTFS における地理的位置の定義に stops.txt はもはや不可欠ではなくなる可能性があります。作成者は、ゾーンベースのデマンド型サービスに locations.geojson のみを使用できるため、stops.txt は条件付き必須になります（locations.geojson が存在しない場合のみ）。GTFS validator の調整により、この変更に対応します。

**[GTFS 用語の改善: 「Schedule」から「Static」への移行 #442](https://github.com/google/transit/issues/442)**

この issue では、データセットをより適切に表すため、GTFS ドキュメントにおける「Schedule」を「Static」に変更することを提案しています。明確性のために、コミュニティから大きな支持があります。この提案には、ドキュメントの更新が含まれます。Pull Request 段階へ進む前に、次のステップに関するフィードバックが推奨されます。
