# GTFS Schedule と Realtime の使い分け {: #when-to-use-gtfs-schedule-vs-realtime}

## はじめに {: #introduction}


現在、GTFSプロデューサーには、公共交通サービスの変更または障害に関する情報を伝えるための選択肢として、[GTFS Schedule](../../../documentation/schedule/reference/)、[GTFS Realtime](../../../documentation/realtime/reference/)、またはその両方の組み合わせがあります。しかし、各形式をいつ使用するべきか、またそれらがどのように連携するべきかについてのガイダンスは限られています。この明確さの欠如は、一貫性のない実装やGTFSコンシューマー間の混乱を招く可能性があり、最終的には公共交通の乗客が利用できる情報の品質に影響を及ぼします。

この文書は、特別サービスおよび／またはサービスの変更や調整を伝えるために、GTFS ScheduleおよびGTFS Realtimeを効果的に使用するためのガイダンスを提供します。各フィードで想定されるユースケースを明確にし、それらの補完的な役割を概説し、実務における各標準の効果的な利用を支援することを目的としています。GTFSプロデューサーとコンシューマーの間でこれらの実践について認識を合わせることにより、解釈の曖昧さを減らし、統合を簡素化し、公共交通利用者に提供される情報の品質と正確性を向上させることを目指します。

## GTFS Schedule と GTFS Realtime の概要 {: #overview-of-gtfs-schedule-and-gtfs-realtime}


GTFS Schedule データは、あらゆる GTFS 実装の基盤となります。名前が示すとおり、このデータセットには、フィードが対象とする期間中に運行される予定のすべてのスケジュール済みサービスが含まれます。

これに対し、GTFS Realtime は、複数の種類のフィードを通じて、スケジュール済みの GTFS データに動的な更新を提供します。[便の更新(trip update)](../../../documentation/realtime/feed-entities/trip-updates/)フィードは、遅延、運休、およびその他のスケジュール変更を表します。[車両位置情報(vehicle position)](../../../documentation/realtime/feed-entities/vehicle-positions/)フィードは運行中の車両のリアルタイム位置を提供し、[運行情報(alert)](../../../documentation/realtime/feed-entities/service-alerts/)フィードは、利用者に伝達するべき障害、迂回、またはその他の重要な状況に関する通知を伝達します。最後に、実験的な[便の変更(trip modification)](../../../documentation/realtime/feed-entities/trip-modifications/)フィードにより、事業者はサービス変更を反映するため、静的なスケジュールを超えて便を調整できます。

GTFS のこれら2つのコンポーネントは、共存し相互に補完するよう設計されています。これらは連携して、計画どおりの運行と実際の運行の両方について、乗客に公共交通サービスの最も正確かつ最新の情報を提供します。

一般的な経験則として、**事業者はサービス情報の主要かつ正式な情報源として、GTFS Schedule をデフォルトで使用するべきです**。GTFS Realtime は非常に有用ですが、実際のサービスが計画から逸脱する場合を除き、スケジュール済みデータを置き換えることを意図したものではありません。

車両位置情報の報告に加えて、GTFS Realtime は選択的かつ戦略的に使用するべきです。つまり、静的フィードに反映するには遅すぎるタイミングで発生した遅延、運休、経路変更、または緊急事態を報告するために使用するべきです。その役割は、スケジュール済みデータを上書きするのではなく、更新または拡張することです。正確かつ最新のスケジュールを維持せずに Realtime データへ過度に依存すると、利用者にとって不整合が生じ、乗客の混乱につながる可能性があります。

以降のセクションでは、この一般原則が特定のシナリオにどのように適用されるかを説明し、各データソースを効果的に使用するタイミングと方法について、より詳細なガイダンスを提供します。

## 重要な考慮事項 {: #important-considerations}

### GTFS RealtimeよりGTFS Scheduleを優先する {: #prioritize-gtfs-schedule-over-gtfs-realtime}


何よりもまず、GTFSを使用して運行情報を公開する際には、**GTFS利用者が更新された情報を各自のプラットフォームで処理、検証、および配信するための十分な時間を確保できるよう、GTFS Scheduleフィードを通じて更新を計画し、公開することを優先するべきです**。

予期しない変更や直前の変更が発生した場合は、GTFS Realtimeを使用して、運休・障害、遅延、または一時的な運行変更を伝達するべきです。これは静的な時刻表を動的に補完するものであり、計画が予期せず変更された際に、乗客がタイムリーな更新を受け取れるようにします。

公式の[GTFS Schedule Reference](../../../documentation/schedule/reference/)より:

> *「常に、公開されたGTFS \[Schedule\]データセットは、少なくとも今後7日間有効であるべきです… 運行変更が7日以内に有効となる場合、この運行変更は静的GTFSデータセットではなく、GTFS Realtimeフィード（運行情報または便の更新）を通じて表現するべきです。」*

また、多くの交通事業者は、高品質なGTFS Realtimeフィードを継続的に生成するための技術的能力やインフラストラクチャを備えていない可能性があることを認識することも重要です。これは、利用者と提供者の双方にとって、可能な限りGTFS Scheduleを優先するべきであるもう1つの理由です。

### 円滑なデータ引き渡しを確保する {: #ensure-a-smooth-data-handover}


軽微なものも含め、サービスの変更や障害は、特に高頻度または大規模な交通システムにおいて、乗客に影響を与える可能性があります。したがって、正確な情報がエンドユーザーに届くことを確保するうえで、提供者から利用者への GTFS データの引き渡しは重要な段階です。これを達成するためには、予測可能性、透明性、および定期的な保守が鍵となります。

問題が発生した際に提供者と利用者が容易に連絡を取れるべきである一方で、**一貫した更新頻度および予測可能な動作を確立することで、アドホックな連絡への依存を最小限に抑えるべきです**。これにより、利用者は変更を予測し、データの正確性を維持しやすくなります。

提供者は、`feed_info.txt` など、フィードに関する明確かつ透明性の高いコミュニケーションを支援する既存の GTFS 機能も活用するべきです。さらに、可能な場合は公開変更履歴または issue tracker を維持することが推奨されます。これにより、利用者はリリース間の変更を追跡し、取り込みプロセスをより効率的に適応させることができます。

### データ伝播のための時間を確保する {: #allow-time-for-data-propagation}


フィードを更新する際、GTFS producerは、新しいフィードバージョンが公開された後、GTFS consumerが新しいデータを取り込み、処理するための時間を必要とすることを考慮するべきです。システムの規模と複雑さに応じて、これには数時間から数日かかることがあります。

GTFS producerは、運行変更が有効になる十分前に更新されたScheduleフィードを公開し、consumerが品質確認を実施し、潜在的な問題を特定するための十分な時間を確保することが推奨されます。このバッファ期間により、新しい運行計画が開始される前に、予期しない問題が検出された場合、consumerはproducerに連絡して問題を報告したり、回避策を実装したりすることもできます。

データ伝播のための時間を確保するには、更新された情報が新しい運行計画の有効化**少なくとも5日前**までにエンドユーザーに提供されることを確実にするため、producerとconsumerが協力して公開および取り込みのプロセスを完了する必要があります。十分な時間があれば、旅行者は最も正確な情報から利益を得られます。

## Schedule と Realtime？ {: #schedule-or-realtime}


サービス情報が乗客に効果的に伝達されるようにするには、主に GTFS Schedule と GTFS Realtime のどちらに依存するかを判断することが不可欠です。両方の形式は補完的な役割を果たしますが、推奨される使用方法は、サービス変更または更新の期間と性質に応じて異なります。 

以下の表は、状況の種類に基づいて、事業者が GTFS Schedule または GTFS Realtime の使用を優先する際の一般的な指針を示しています。

|  | **短期間（数時間から数日）** | **長期間（数週間から数か月）** |
|---|---|---|
| 計画されたサービス | *GTFS Schedule を使用する対象*<br>- 祝日ダイヤ<br>- 計画された大規模イベント期間中の特別サービス<br>- 事前告知を伴う一時的な迂回<br>- 予定された早期閉鎖 | *GTFS Schedule を使用する対象*<br>- 通常サービス<br>- 季節的なダイヤ改正<br>- 影響が判明している工事<br>- ルート・路線系統(route)の再設計<br>- サービスの拡大または縮小 |
| 予期しないサービス障害 | *GTFS Realtime を使用する対象*<br>- 車両故障による便(trip)の運休<br>- リアルタイムの遅延<br>- 緊急迂回<br>- 事故<br>- 予期しない需要の変化 | *両方を組み合わせて使用する対象*<br>- 長期化するストライキまたはデモ<br>- 自然災害またはその他の事象によるインフラ損傷<br>- 継続的な車両不足<br>- 事故後の長期的な駅閉鎖 |

このマトリックスは、決定的または絶対的な指針ではないことに注意してください。サービス障害は複雑で微妙な場合があります。それぞれの状況に適切に対応するためには、柔軟性が不可欠です。主な目標は、乗客が旅程を効果的に計画できるよう、正確でタイムリーな情報を提供することです。

以降のセクションでは、計画されたサービス更新と予期しないサービス更新の両方について、推奨される実践方法を詳しく説明します。

### 計画されたサービス: 短期および長期 {: #planned-services-short-and-long-term}


交通事業者は一般に、規則的で予測可能な時刻表を提供することを目指し、効率を最大化するために運行を慎重に計画します。これらの計画の一部は一定期間安定したままであることがありますが、運用上の制約、特別なイベント、季節的な変化など、さまざまな理由によりサービスはしばしば調整または適応されます。

公式の[GTFS Schedule reference](../../../documentation/schedule/reference/)によると、*「GTFS dataset は少なくとも今後7日間有効であるべきであり、理想的には、運行事業者が時刻表の運行継続に確信を持てる期間と同程度の期間、有効であるべきです。」* 大規模なサービス変更が不要な場合でも、フィードに含まれる運行時刻表が正確かつ最新の状態に保たれるよう、作成者は**GTFS feeds の定期的かつ周期的なメンテナンス**を実施することが期待されます。

GTFS Schedule には、ルート・路線系統(route)、便(trip)、停留所等(stop)、時刻表など、交通システムにおける不可欠な計画要素が含まれており、あらゆる GTFS 実装の基盤となるため、これらの更新では GTFS Schedule を使用して、すべての計画されたサービスを表現するべきです。計画されたサービスには、通常運行（例: 平日および週末のサービス）だけでなく、休日時刻表、季節に応じて調整された時刻表、主要な計画イベント（例: スポーツイベントまたはコンサート）に伴うサービス変更など、今後予定されている特別サービスも含まれます。

一時的なルート変更、駅の閉鎖、便の運休など、事前に判明している計画されたサービス中断または運行変更も、**可能な限り早期に** Schedule feed に組み込むべきです。最新の Schedule feed を維持することで、経路検索サービスおよびその他の利用者が、十分に前もって正確な情報をユーザーに提供できるようになります。

以下の表は、計画されたサービスの最も一般的なケースを要約し、いくつかの例を示します。

| **ユースケース** | **説明** | **例** |
|---|---|---|
| 通常サービス | 一貫した時刻表に従う、標準的かつ反復的なサービスです。 | - 平日の通勤サービス<br>- 週末の減便運行<br>- 深夜バスサービス |
| 特別サービス | 特定の機会または期間に合わせて予定され、事前に判明しているサービスです。 | - 休日時刻表（例: クリスマス、元日）<br>- 夏期または冬期時刻表<br>- 主要イベント（例: スポーツイベントまたはコンサート）向けの特別サービス |
| 計画されたサービス中断 | 保守またはその他の事前に予定されたイベントにより生じる、通常サービスへの既知の変更です。 | - 一時的な駅の閉鎖<br>- 工事に伴うルート迂回<br>- 保守に伴う予定された便の運休 |

計画されたサービスに対する定期的なフィード更新のために、信頼できる環境を構築する目的で、以下の実践が推奨されます。

### 計画的なサービス調整における GTFS Realtime の補完的な使用 {: #complementary-use-of-gtfs-realtime-for-planned-service-adjustments}


GTFS Schedule は計画されたサービス更新を伝えるための主要な情報源であり続けるべきですが、GTFS Realtime Service Alerts は、今後発生する運行障害や調整をユーザーに通知することでこれを補完します。

例えば、夏季ダイヤの開始前や、大規模工事に伴うルート・路線系統(route)の一時的な迂回の前に、ユーザーに知らせて適切な計画を可能にするため、変更の数日前に（すでに GTFS Schedule フィードに反映されている）Service Alert を公開することができます。

ほとんどの場合、計画的な調整に関する Service Alerts は、**変更の発効日の7日前を超えて公開するべきではありません**。この機能のサポートは、コンシューマーによって異なる場合があります。

#### 推奨プラクティス {: #recommended-practices}


**提供者**

  * **Schedule フィードの予測可能な更新サイクルを確立してください:** 適切な頻度は、各事業者の運用状況によって異なります。一部の事業者は毎週または毎月更新することができますが、他の事業者は四半期ごとに更新します。予測可能なサイクルは、利用者が変更を予測し、更新に備えるのに役立ちます。  
  * **更新された Schedule フィードを事前に公開してください:** 理想的には、変更が判明し次第フィードを公開するべきですが、運行変更が発効する **3～4週間** 前に更新をリリースすれば十分です。予期しない変更が発生した場合でも、提供者は、新しい運行計画が有効になる **少なくとも7日間（7日）** 前に更新された GTFS Schedule フィードをリリースすることを目指すべきです。運行変更がそれより短い期間で判明した場合、対応する GTFS Realtime を使用して変更を反映するべきです。  
  * **`feed_info.txt` を使用してフィードの主要な詳細を伝達してください:** 正確な連絡先情報（`feed_contact_email`、`feed_publisher_name`、`feed_publisher_url`）、`feed_start_date`、`feed_end_date`、および `feed_version` を含めてください。この情報は、利用者が最新のデータを使用していることを確認し、問題が発生した場合に提供者へ連絡するのに役立ちます。Realtime フィードと Schedule フィードの両方に `feed_version` を含めることで、正しいデータが取り込まれていることについて追加の確実性が得られます。  

**利用者** 

  * **新しいフィードバージョンを毎日確認してください:** 利用者は、リリースから **48時間** 以内に新しいデータを取り込むことが期待されており、これにより、正確な運行情報が変更の発効する **少なくとも5日間（5日）** 前にエンドユーザーに提供されます。

##### 例1: 大規模コンサート前後の運行調整 {: #example-1-service-adjustment-around-a-major-concert}


大勢の観客を集めると予想される重要なコンサートが、**5月24日**に開催されることが発表されます。交通事業者はこのイベントを6か月前から把握しており、会場を運行するルート・路線系統(route)において**夜間運行を延長**する計画です。これは計画的な調整であるため、通常の保守更新の一環として**GTFS Schedule feed**に反映しなければなりません。

| 日付 | イベント | 詳細 |
|------|-------|---------|
| **3月31日** | 運行計画の確定 | - 事業者は数か月前にコンサートを把握し、追加運行の必要性を特定します。</br>- 事業者は、**3月31日**に特別イベント運行を含む5月の完全な運行計画を確定します。 |
| **4月10日** | 更新済みGTFS Scheduleの公開 | - 事業者のGTFS保守担当チームは、特別な便(trip)および調整済み時刻表を含む5月のデータセットを準備します。</br>- 更新済みのSchedule feedは、**4月10日**に事業者のオープンデータポータルで公開されます。</br>- これには、現在の時刻表と将来の時刻表を組み合わせた、5月および4月の残りの運行情報が含まれます。 |
| **4月10日～14日** | コンシューマーによる取り込み | - 経路検索アプリケーションは、公開された当日に更新を検出します。</br>- これらはfeedを取り込み、品質チェックを実行し、**4月14日**までに更新済みの5月時刻表をユーザーに表示し始めます。 |
| **5月22日** | Realtime Service Alertの追加 | - 間近に迫った変更の視認性を高めるため、事業者はイベントの2日前である**5月22日**にService Alertを公開します。</br>- 経路検索アプリは数分以内にalertの表示を開始します。</br>- このalertは、すでに利用可能なSchedule情報を補完します。 |
| **5月25日** | Service Alertの削除 | - イベント後、事業者はRealtime feedからalertを削除します。</br>- 経路検索アプリは直ちにその表示を停止します。 |

##### 例2: 夏季ダイヤの開始 {: #example-2-start-of-summer-schedule}


夏季シーズンに先立ち、ある交通事業者は、複数のバスルート・路線系統(route)の運行頻度を調整し、季節限定のビーチシャトルを復活させる季節ダイヤを計画しています。この季節計画は**6月1日**に開始し、ほぼ4か月間継続します。これらは計画済みの定期的な変更であり、事業者の通常の更新サイクルの一環として、**GTFS Schedule** フィードに反映しなければなりません。乗客が移行に備えられるよう、事業者は変更が有効になる直前に、今後の変更を強調するため **GTFS Realtime Service Alerts** も使用します。

| 日付 | イベント | 詳細 |
|------|-------|---------|
| **5月2日** | 夏季ダイヤの確定 | - 事業者は数か月前から、複数のバスルート・路線系統(route)における運行頻度の調整と、季節限定のビーチシャトルの再導入を含む夏季運行計画を準備します。</br>- 更新されたダイヤは**5月2日**に確定します。 |
| **5月14日** | 更新された GTFS Schedule の公開 | - 事業者の GTFS の保守を担当するチームは、特別な便(trip)と調整済みのダイヤを含む6月のデータセットを準備します。</br>- 6月1日に有効となる夏季運行の変更と、5月の残りの運行を含む6月の Schedule フィードが、**5月14日**に公開されます。 |
| **5月14日～18日** | コンシューマーによる取り込み | - 経路検索アプリケーションは、更新された Schedule が公開されるとすぐに検出します。</br>- これらのアプリケーションはフィードを取り込み、品質チェックを実行し、**5月18日**までに乗客に6月の運行変更を表示し始めます。 |
| **5月25日** | Realtime Service Alert の追加 | - 夏季ダイヤに対する認知度を高め、乗客に今後の変更を知らせるため、事業者は変更が有効になる1週間前の**5月25日**に GTFS Realtime Service Alert を公開します。</br>- 運行情報の説明は次のとおりです。*"夏季ダイヤは6月1日に開始します。一部のサービスでは通常の運行頻度が変更され、季節限定のビーチシャトルが運行します。詳細については当社のウェブサイトをご確認ください。"* </br>- 経路検索アプリは数分以内に運行情報の表示を開始します。 |
| **6月6日** | Service Alert の削除 | - 事業者は**6月6日**に Realtime フィードから運行情報を削除し、乗客が移行前と移行直後の両方で確認できるようにします。</br>- 経路検索アプリは直ちにその表示を停止します。 |

### 予期しない短期間の運行障害 {: #unforeseen-short-term-service-disruptions}


慎重に計画していても、公共交通サービスは、短期間に運行を妨げる突発的な事象の影響を受けることがよくあります。例としては、車両故障、軽微な事故、一時的な迂回、緊急閉鎖、または短期間の需要急増が挙げられます。

これらの事象はほとんど、またはまったく予告なく発生するため、事業者は迅速に対応しなければならず、多くの場合、GTFS データチームには Schedule feed を変更するための十分な時間が残されていません。これらの短期間の調整を GTFS Schedule で表現しようとすることは現実的ではなく、通常運行が再開された後に一時的な変更を削除する必要があるため、エラーを招く可能性があります。

したがって、GTFS Realtime は短期間の障害を伝達するための最も効果的な手法です。Schedule feed を補完することで、Realtime updates は、計画されたスケジュールを維持しながら、事業者が運行上の変更を即座に伝達することを可能にします。場合によっては、Realtime updates が一時的に Schedule データを上書きすることさえありますが、**producer はそのような発生を最小限に抑えるべきです**。

Realtime feeds は頻繁な更新をサポートしており、consumer applications が継続的に、または短い間隔でデータを取り込めるようにすることで、乗客が最新の情報を受け取り、リアルタイムで十分な情報に基づく判断を行うことを支援します。

[GTFS Schedule Reference](../../../documentation/schedule/reference/) に記載されているとおり、*更新された GTFS Schedule feed を、サービス変更の発効日の少なくとも 7 日前までに公開できない場合は、その変更を GTFS Realtime を通じて伝達するべきです*。この期間を満たせるかどうかを判断する際、producer は、データ準備、内部検証、公開、および consumer が更新されたデータセットを取得、処理し、アプリケーションにデプロイするために必要な時間を含む、エンドツーエンドのプロセス全体を考慮するべきです。

GTFS Realtime は、更新を提供するために使用できる 4 種類の異なるエンティティで構成されています: **Service Alerts、Trip Updates、Vehicle Positions** および **Trip Modifications**（現在は実験的機能です）。これらの feed entities は、状況に応じて、単独または組み合わせてサービス更新を表現するために使用できます。各エンティティに関する詳細については、[GTFS Realtime Reference](../../../documentation/realtime/reference/) を参照してください。

#### 推奨事項 {: #recommended-practices}


**プロデューサー:**

  * **Realtime データと Schedule データ間の識別子の一貫性を確保してください:** `trip_id`、`route_id`、`stop_id` など、スケジュールされたサービスを参照する Realtime エンティティは、対応する GTFS Schedule フィードで公開されている識別子と一致しなければなりません。これにより、コンシューマーは Realtime の更新をスケジュールされたサービスに正しく関連付けることができ、データ取り込み、信頼性、およびユーザー向けの正確性が向上します。  
  * **正しい Schedule フィードのバージョンへの明確な参照を含めてください:** プロデューサーは、Realtime フィードがどの GTFS Schedule データセットに対応しているかを示すために、GTFS Realtime（および `feed_info.txt`）の `feed_version` フィールドを設定するべきです。これにより、コンシューマーは Realtime データが適切なバージョンの Schedule フィードにマッピングされていることを検証でき、頻繁な更新や運用変更の期間における不整合の問題を軽減できます。  
  * **GTFS Realtime で作成される新規または置換の便(trip)への過度な依存を避けてください:** GTFS Realtime における新規または置換の便(trip)の作成は、控えめに、かつ運用上必要な場合（例: 予定外の追加サービス）にのみ使用するべきです。Realtime で追加された便(trip)に過度に依存すると、コンシューマーによる取り込みが複雑になり、サービスの予測が困難になり、計画されたサービスと実際に運行されたサービスの間で不整合が生じる可能性があります。可能な場合は常に、GTFS Schedule および/または Realtime の Trip Modifications の使用を優先してください。  
  * **Realtime 情報が有効でなくなった場合は削除してください:** プロデューサーは、解消済みの運行情報(alert)、期限切れの迂回、完了した運休などの古い Realtime データが、現在のサービスを反映しなくなった時点で速やかに削除されるようにするべきです。適時の削除により、ユーザーの混乱を防ぎ、Schedule 情報と Realtime 情報の間で競合が生じるリスクを軽減し、コンシューマーが有効なサービス状況を正確に表現し続けることを支援します。

**コンシューマー:**  

  * **検出したデータの問題をプロデューサーに積極的に伝えてください:** 不整合なカレンダー、欠落したジオメトリ、継続的な識別子の競合、予期しない便(trip)の動作などの問題が発生した場合、コンシューマーは確立されたコミュニケーションチャネルに従い、速やかにプロデューサーへ通知するべきです。早期のフィードバックにより、より迅速な修正が可能になり、より広範なデータエコシステムに利益をもたらします。

##### 例3: 停電による一時的な駅閉鎖 {: #example-3-temporary-station-closure-due-to-power-outage}


11月8日、予期しない停電により、当局は市のOrange Subway Lineを運行する重要な駅を一時的に閉鎖せざるを得なくなります。この停電は予期しないものであり、電力が復旧するまで駅を直ちに閉鎖する必要がありますが、列車は影響を受けた駅を通過するだけで、システムの他の部分では通常どおり運行を継続できます。混乱は約1時間続くと予想されるため、事業者は一時的なサービス中断を伝達するために全面的に**GTFS Realtime**に依存します。

| 時刻 | イベント | 詳細 |
|------|-------|---------|
| **11月8日（午後4時45分）** | 停電を検知 | - 午後4時45分頃、Oakwood Stationは停電により直ちに閉鎖を余儀なくされます。 |
| **11月8日（午後5時15分）** | GTFS Realtimeフィードの更新 | - 事業者は、駅が一時的に閉鎖されていることを乗客に通知し、混乱の予想継続時間を示す運行情報を追加するために、**GTFS Realtime Service Alerts**フィードを更新します。</br>- 同時に、影響を受ける便において当該駅を`skipped`としてマークするために、**GTFS Realtime Trip Updates**フィードが使用され、車両がOakwood Stationに停車しないことを効果的に伝達します。</br>- 経路検索アプリケーションはRealtimeフィードを即座に取り込み、経路検索ツールのユーザーインターフェースに運行情報を表示するとともに、経路検索上でOakwood Stationを閉鎖し始めます。</br>- 乗客は閉鎖について通知を受け、それに応じて旅行計画を調整できます。 |

##### 例4: 緊急道路閉鎖によるバス運行の調整 {: #example-4-adjusted-bus-service-due-to-emergency-road-closure}

| 時刻 | イベント | 詳細 |
|------|-------|---------|
| **6月12日（午前9時30分）** | 緊急道路閉鎖を検知 | - ルート・路線系統(route) 17を使用する便(trip)は、突然の水道本管破裂により影響を受け、バスは代替の大通りを経由して迂回する必要があり、3つの停留所等(stop)を通過せず、遅延が発生します。 |
| **6月12日（午前10時00分）** | GTFS Realtime フィードの更新 | - 事業者は、当日の残りの時間においてルート・路線系統(route) 17で遅延が予想されることを示す運行情報を追加するため、**GTFS Realtime Service Alert**フィードを更新します。</br>- **GTFS Realtime Trip Updates**フィードを使用して、影響を受ける3つの停留所等(stop)を`skipped`としてマークし、当日の対応する便(trip)に推定遅延を割り当てます。</br>- 経路検索アプリケーションはRealtimeフィードを直ちに取り込み、経路検索ツールのユーザーインターフェースに運行情報を表示し始めるとともに、経路検索の目的で影響を受ける3つの停留所等(stop)を無効化します。</br>- 乗客は遅延および休止された停留所等(stop)について通知を受け、それに応じて旅行計画を調整できます。 |

| **6月14日（午後11時00分）** | 修理完了、翌日に通常運行を再開 | - 6月14日の午後10時30分頃、水道本管の修理作業が完了し、交差点は数時間後に再開通できる状態になります。</br>- 交通事業者は、対応する運行情報および便(trip)の更新をGTFS Realtimeフィードから削除します。</br>- 経路検索アプリケーションは更新されたフィードを反映し、GTFS Scheduleからの通常運行情報を再度有効化し、運行情報を削除します。 |

### 予期しない長期的な運行障害 {: #unforeseen-long-term-service-disruptions}


時として、予期しないまたは突発的な事象により、中期的または長期的な運行障害が発生し、通常運行がいつ再開されるかについて高い不確実性が生じることがあります。例としては、公共交通機関の運行を妨げる自然災害、特定のルートを長期間にわたり封鎖するストライキやデモ、または駅の無期限閉鎖を余儀なくする構造的な損傷が挙げられます。

このような障害が発生した場合、**プロデューサーはまず GTFS Realtime を通じて影響を伝達し、利用者が即時かつ正確な情報を受け取れるようにするべきです**。予想される期間および運用上の影響についてより明確になった時点で、プロデューサーは調整後の運行期間の残りの期間に向けた情報伝達戦略を策定するべきです。

適切なアプローチは、障害の性質と期間、および事業者のデータ管理能力によって異なります。ただし、以下の一般的なガイダンスが適用されます。

* **事業者は、1週間を超え1か月未満続く障害について、GTFS Schedule と GTFS Realtime のどちらを使用するか選択することができます。** これは、運用上の制約、更新ワークフロー、および運行パターンの変更が予想される頻度に依存します。GTFS Schedule の更新が実現不可能または実用的でない場合、プロデューサーは、より安定した運行計画を策定できるまで、運休、追加便、調整後のパターン、またはその他の運行変更を伝達するために GTFS Realtime に引き続き依存することができます。  
* 可能な場合、**障害が1か月を超えて継続すると予想される場合は、調整後の運行を表すために GTFS Schedule の使用を優先するべきです**。GTFS Schedule は、数週間または数か月にわたる運行パターンをより信頼性が高く永続的に表現できます。GTFS Realtime Service Alerts は、継続中の影響を強調したり、追加の文脈を提供したりする補完的なチャネルとして引き続き使用できます。

プロデューサーとコンシューマーは協力し、状況の変化に応じて継続的に再評価し、乗客にとっての明確性、正確性、および使いやすさを維持するために、情報伝達戦略をそれに応じて更新するべきです。

#### 推奨プラクティス {: #recommended-practices}


**プロデューサー:**

* **コンシューマーとの積極的かつ継続的なコミュニケーションを維持してください:** 長期にわたる障害時には、運用状況の変化に伴い、サービス計画が頻繁に変化することがあります。コンシューマーが遅延なく新しいデータを準備および取り込めるように、プロデューサーは想定されるタイムライン、計画されたデータ更新、戦略の変更可能性（例: Realtime から Schedule への切り替え）を伝達することが推奨されます。  
* **Realtime から GTFS Schedule への構造化された移行を確保してください:** 障害が GTFS Schedule の更新を正当化する安定度に達した場合、プロデューサーは、新しい Schedule feed が有効になった時点で一時的な Realtime メッセージおよび便(trip)の調整が削除または更新されるよう、移行を明確に調整するべきです。  
* **非常に短い有効期間のみを対象とする Schedule feeds の公開を避けてください:** 調整後のサービスを表すために GTFS Schedule を使用する場合、プロデューサーは、短期間のみを対象とする複数の feeds（例: 数週間のみを対象とするもの）の発行を避けるべきです。代わりに、Schedule の更新は、合理的に安定した有効期間を持つサービスパターンを反映するべきです。  
* **Schedule の更新を補完するために Realtime Service Alerts を使用してください:** 長期的な障害に対して更新済みの Schedule feed が公開されている場合でも、Realtime は引き続き有用なコンテキストを提供できます。たとえば、影響を受ける駅を強調したり、安全情報を提供したり、予想される運行の変動を通知したりできます。  

**コンシューマー:**

* **主要な更新またはコミュニケーション戦略の変更を予測するため、プロデューサーと調整してください:** 特別な状況では、コンシューマーは、想定されるタイムライン、計画された公開日、および取り込みや表示に影響を及ぼす可能性のある複雑性を理解するために、プロデューサーと積極的に連携するべきです。早期の調整により、不整合のリスクが軽減され、乗客向けシステムが新しい情報を迅速かつ正確に組み込むことが確保されます。

##### 例5: 地震被害後の無期限の駅閉鎖 {: #example-5-indefinite-station-closure-following-earthquake-damage}


8月17日、中規模の地震により、市内のCentral Station（地下鉄システムのRed Lineで最も利用者数の多い停留所等(stop)の1つ）に構造的な損傷が発生します。駅は安全検査のため直ちに閉鎖され、再開時期は明確ではありません。交通事業者は当初、閉鎖を乗客に通知し、状況の進展に応じて更新情報を提供するために**GTFS Realtime**を利用します。

| 日付 | イベント | 詳細 |

| **8月17日** | 地震および初期閉鎖 | - 駅は構造的損傷のため直ちに閉鎖されます。</br>- Red Lineの便(trip)がCentral Stationに停車しないこと、および同駅が追って通知があるまで閉鎖されたままであることを乗客に通知するため、**GTFS Realtime Service Alert**が公開されます。</br>- **Trip Updates feed**は、StopTimeUpdate内でCentral Stationを`skipped`としてマークすることにより、影響を受ける便(trip)を調整するために使用されます。 |

| **9月1日** | 更新されたService Alert | - 事業者は、影響を受ける便(trip)の調整にTrip Updates feedを使用することを停止し、代わりにGTFS Schedule feed内の更新された運行データに依存します。</br>- 事業者は、駅が少なくとも**10月31日**まで閉鎖されたままであることを伝える新しいService Alertに、以前のService Alertを置き換えます。</br>- 経路検索アプリは、数分以内に更新された運行情報(alert)の表示を開始します。 |
| **10月20日** | 駅再開日確定、更新されたGTFS Scheduleの公開 | - 事業者は、10月最終週に修理が完了した後、駅が**11月1日**に再開することを確認します。</br>- **10月20日**、事業者は更新されたScheduleを事業者のオープンデータポータルで公開します。</br>- これには11月の運行情報と10月の残りの期間の運行情報が含まれ、現在のスケジュールと将来のスケジュールを組み合わせます。 |
| **10月22日** | 利用者向け取り込み | - 経路検索アプリケーションは、リリース当日に更新を検出します。</br>- これらはfeedを取り込み、品質チェックを実行し、**10月22日**までに更新された11月のスケジュールをユーザーに表示し始めます。 |
| **10月22日** | Realtime Service Alertの追加 | - 駅の再開予定について乗客に通知するため、事業者は駅での運行再開の1週間前である**10月22日**にService Alertを公開します。</br>- 経路検索アプリは数分以内に運行情報(alert)の表示を開始します。</br>- この運行情報(alert)は、すでに利用可能なSchedule情報を補完します。 |
| **11月3日** | Service Alertの削除 | - 再開の2日後、事業者はRealtime feedから運行情報(alert)を削除します。</br>- 経路検索アプリは直ちにその表示を停止します。 |

##### 例6：職員ストライキによる予期しない長期的なサービス中断 {: #example-6-unforeseen-long-term-service-disruption-due-to-staff-strike}


**3月3日**、市内全域の地下鉄、バス、トラムの特定時間帯の運行に影響する交通機関職員のストライキが発表されます。事業者は当初、ストライキがどのくらい続くかを把握しておらず、乗客にとって不確実性が生じるため、即時かつ継続的な情報提供が必要となります。事業者は、中期的なサービス調整の可能性を評価しながら、その影響を伝えるために **GTFS Realtime** を利用します。

| 日付 | イベント | 詳細 |
|------|-------|---------|
| **3月3日** | ストライキ開始 | - すべての交通サービスは、最初の毎日の運休時間帯（**午前10:00～午後4:00**）に中断され、その後徐々に運行を再開します。</br>- 中断について乗客に通知するため、想定される運休時間帯および限定的な運行を含む **GTFS Realtime Service Alert** が公開されます。</br>- **GTFS Realtime Trip Modifications** フィードは、運休時間帯内の便をキャンセルし、運行する便を調整するために使用されます。 |
| **3月3日～10日** | Realtime 更新のみ | - 事業者は、各日の運休時間帯および変更されたスケジュールについて、毎日 Realtime 更新を提供します。</br>- ストライキの展開に応じて、**Service Alerts** は頻繁に更新されます。</br>- **Trip Modifications** は、キャンセルおよび調整された運行パターンを引き続き反映します。 |
| **3月10日** | 想定されるストライキ期間の確定 | - 交渉の結果、事前に合意に達しない場合、順次行われる運休は **月末まで継続する** と見込まれることが示されます。</br>- 事業者は、一貫した毎日の運休時間帯や、それらの時間帯以外での調整された運行頻度を含め、運行上の不確実性を減らすため、より安定した一時的な運行計画の策定を開始します。</br>- 状況が流動的であり、合意に達した場合にはストライキが突然終了する可能性があることから、事業者は、安定したパターンを完全に実施できるまで、調整後の運行スケジュールを伝えるために **GTFS Realtime** への依存を継続することを決定します。 |
| **3月11日～23日** | Realtime 更新を継続 | - 事業者は、各日の運休時間帯および変更されたスケジュールについて、毎日 Realtime 更新を引き続き提供します。</br>- 乗客に中断を知らせ続けるため、**Service Alerts** の使用を継続します。</br>- **Trip Modifications** は、キャンセルおよび一時的なサービス調整を引き続き反映します。 |
| **3月23日** | ストライキ終了 | - 事業者と労働組合の間で合意に達し、ストライキは実質的に終了し、翌日の通常運行再開が可能になります。</br>- 事業者は、通常運行が3月24日に再開される見込みであることを乗客に通知する更新済みの **Service Alert** を公開します。</br>- 経路検索アプリは数分以内に運行情報を表示し始めます。 |
| **3月24日** | 通常運行への移行 | - **Trip Modifications** および以前の **Service Alerts** は削除され、標準的な運行情報の提供には **GTFS Schedule feed** が使用されます。</br>- 事業者は、通常運行が現在実施されていることを確認する更新済みの **Service Alert** を公開します。</br>- 経路検索アプリは数分以内に運行情報を表示します。 |
| **3月26日** | Service Alert を削除 | - 事業者は、通常運行の再開から2日後に Realtime フィードから運行情報を削除します。</br>- 経路検索アプリは直ちにその表示を停止します。 |

サービスの中断および運行上の変更は予測が難しいことが多いものの、GTFS Schedule と GTFS Realtime を補完的に使用することで、乗客がこの不確実性に単独で対処することがないようにすることができます。 

本書では、交通事業者およびデータ利用者が日常業務で遭遇する最も一般的なシナリオの多くについて、推奨される実践方法を示しました。しかし、現実の状況はより複雑である可能性があり、追加の調整や状況に応じたアプローチが必要になる場合があります。

疑問が残る場合、または状況がここで扱った例の範囲外である場合、事業者および利用者は、助言を求め経験を共有するために、より広範な [GTFS Community](../../community/get-involved/) に参加することが推奨されます。同業者から学び、新たなユースケースについて議論することは、実装を強化し、データ提供者と乗客の双方にとっての成果を改善するのに役立ちます。
